# Testing

## Running the tests

From MATLAB:

```matlab
cd tests
runTests
```

From WSL (headless):

```bash
"/mnt/c/Program Files/MATLAB/R2025b/bin/matlab.exe" -batch "cd tests; runTests"
```

`runTests` errors when a test fails, so a `-batch` run exits non-zero.

If that command fails with `Exec format error` or a screen of `not found` / `Syntax error` lines, WSL cannot run Windows programs: its interop is not registered (systemd in `/etc/wsl.conf` often clears it). It is not a MATLAB problem. In a WSL terminal:

```bash
sudo sh -c 'echo :WSLInterop:M::MZ::/init:PF > /proc/sys/fs/binfmt_misc/register'
```

## What they cover

## What they do not cover

- **The protocols end to end.** The protocol files need Bpod, the DMD, the NI-DAQ, the HiFi and rotary encoder modules; there are no stand-ins for these yet, so a protocol cannot run under `Bpod('EMU')`. After changing a protocol file, run one short session on the rig.
- **The state machines** (`PrepareStateMachine`): they need Bpod's state-machine functions.
- **The laser connected** (`lhf.laser.open`, `onSoftCode`, `setpoint`): needs the OBIS and the power calibration.
- **Odour delivery on the real valves** (`lhf.olf.startWorker`, `waitWorker` with a DAQ session): needs the NI-DAQ. The worker mechanism itself is tested in the NIDAQOlfactometer repo, on a real one-worker pool with simulated valves.
- **The parameter GUIs**, and the Pattern Designer's dialogs and laser table.
- **Bpod guards on the rig**: stop a session mid-trial, check `timerfindall` has no running timer whose `TimerFcn` mentions `processLiveEvents`, restart, run Calibrate Sniff (finishes after 12 s), and run trials with no `XDataYData` warnings.
- **The calibrations on the rig** (the Calibration window): run each once with its devices, check the plot, Stop one midway (the DMD halts, the laser's emission goes off, the stages return), Save, and check the Laser power result against the old CSV with the PM100D.
- **The camera-DMD calibration and the designer on the rig** (Calibrate: Camera - DMD, the Hamamatsu camera and the DMD): run the calibration, open the designer, place spots on landmarks on the live camera image, tick **Show on DMD** and check the light lands on the drawn squares; again at binning 2 with a subarray.
- **Alignment on the rig** (Calibrate: Stage - camera, **Align to reference**): set `zaber.axes`, run the calibration (about 0.634 px/um), save a reference, move X/Y about 200 um and Z about 30 um by hand, align, and check the stage comes back within 2 um and Stop halts it.

## Soak test (on the rig)

`tests/soak/` runs powercal back to back with a virtual subject until MATLAB crashes, to catch the crashes that end sessions (2026-10: a recurring `libmx.dll` access violation, and MATLAB vanishing). It needs the rig, not the test suite's stand-ins.

- From WSL: `tests/soak/soak.sh [maxTrials]` (default 800, about 2.5 hours) starts a MATLAB of its own running `virtualSessions`. MATLAB must not be open already (the COM ports).
- **What it drives:** Bpod, the HiFi, rotary encoder and sniff input, the odour worker and the DMD, as a session does: LUMI-0022's stimuli, a light cue and CS+ and CS- patterns (powercal's newest designs), so the DMD projects every trial (Sniff Trigger off: with no animal a pattern would wait for a sniff forever). Not the camera: the laser is obis's simulated one (installed as `lhf.device('laser')`, Laser control on, so the power is set every trial). **An operator** (`virtualUser`) acts every 10-40 s with the real pointer and keyboard (`java.awt.Robot`, through MATLAB's event queue as a person's clicks): selects tabs, types a new CS+ probability, reward or ITI, opens the Laser, DMD or Calibration panel (never the Camera, the Pattern Designer or the Stage: the stage must not move) and closes them, pauses and resumes, presses Calibrate Sniff, moves the Live Plots window, and presses Stop at a random trial in about a third of the sessions. Nobody can use the rig's mouse while it runs. Settings: LUMI-0022's, with Training at CS+ probability 0.5 and maxTrials, written to FakeSubject's `VirtualSoak.mat` at each launch (each session saves its settings back there as it ends, so an edit to the file during a run lasts one session; restart the run instead). Until 2026-10-21 both stimuli were odours and the DMD was never opened (19 sessions, no crash).
- **The virtual subject:** a timer licks on BNC input 1 with the serial message Bpod's `ManualOverride` sends (virtual events; not `ManualOverride` itself, whose `drawnow`, run from the timer inside another `drawnow`, once spun MATLAB for 4 minutes), so trials are scored and water is given on hits. That timer is itself a callback acting on `BpodSystem`, the suspected pattern: if a crash comes, repeat without it before blaming the rig.
- **Output:** `D:\luminoseData\soak\<start>\` with `run_log.txt` (each session's start, end, trials, stop reason, MATLAB's memory), `actions.txt` (what the operator did), `leaks.txt` (after each session: timers by name or callback, figures, graphics objects, root appdata, `BpodSystem.Data`'s size, MATLAB's and Java's memory), `matlab_output.txt` (the command window) and `watchdog.txt`. On a crash, `crash/` gets the MATLAB and Windows dumps written since the launch, Windows' events and the session log's tail.
- **Analog data:** each session's `_ANLG.dat` is beside its data in FakeSubject's `Session Data`, as the Launch Manager puts it (in the run folder until 2026-10-21). Sessions started by `RunProtocol('Start', ...)` from code, as here, get no analog data after the first unless the session clock is reset first (`BpodSystem.resetSessionClock()`, as the Launch Manager does): the `'X'` that `RunProtocol('Stop')` sends stops the state machine's analog stream and only `'*'` starts it again. The driver resets it before each session. Sessions started from the Launch Manager are not affected.
- **Stopping:** create `D:\luminoseData\soak\STOP`; MATLAB quits after the current session.
- Windows writes a dump of its own when MATLAB vanishes only if `LocalDumps\MATLAB.exe` is set (admin, `DumpType` 2).

## Adding tests

Add a test for anything added to `+lhf`: one `matlab.unittest.TestCase` class per area in `tests/`, named `<Area>Test.m`, using `fakeTrial`/`fakeSession` for data. Keep tests free of hardware.
